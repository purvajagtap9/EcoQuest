# Deployment Guide

EcoQuest India has three deployable pieces: **MongoDB** (database), **backend** (Spring Boot), **frontend** (React/Vite static site). Recommended free-tier path: **MongoDB Atlas → Render → Vercel**.

Deploy in that order — each piece needs a URL from the one before it.

---

## 1. Database — MongoDB Atlas

1. Create a free account at https://www.mongodb.com/atlas and create a free **M0** cluster.
2. **Database Access** → add a database user (username + password). Save these.
3. **Network Access** → add IP `0.0.0.0/0` (allow from anywhere — required because Render's free-tier outbound IPs aren't fixed; tighten this if you move to a paid plan with static IPs).
4. **Connect → Drivers** → copy the connection string. It looks like:
   ```
   mongodb+srv://<user>:<password>@cluster0.xxxxx.mongodb.net/ecoquest?retryWrites=true&w=majority
   ```
   Replace `<user>`/`<password>`, and make sure the database name (`/ecoquest`) is in the path.

Keep this string — it's your `MONGODB_URI`.

---

## 2. Backend — Render (Docker)

The repo root contains `render.yaml` and `backend/Dockerfile`, so Render can deploy straight from it.

1. Push the project to GitHub (make sure `.env` files are **not** committed — they're in `.gitignore`).
2. On https://render.com → **New → Blueprint** → connect your repo → Render reads `render.yaml`.
3. When prompted, fill in the `sync: false` env vars:
   - `MONGODB_URI` — the Atlas string from step 1
   - `CORS_ALLOWED_ORIGINS` — your frontend URL (you'll know this after step 3; you can leave a placeholder now and update it afterward)
   - `GEMINI_API_KEY` — leave blank unless you want real AI verification
4. `JWT_SECRET` is auto-generated by Render — no action needed.
5. Deploy. First build takes several minutes (Maven downloads dependencies).
6. Verify: `https://<your-service>.onrender.com/api/health` → `{"status":"UP",...}`

**Free-tier caveats (be honest with judges about these in a demo):**
- Render's free web services **sleep after ~15 minutes idle**; the first request afterward takes 30–60s to wake up. Hit `/api/health` a minute before presenting.
- **Uploaded images are stored on the container's local disk**, which Render's free tier does **not** persist across restarts/redeploys. For a real deployment, implement an S3/Cloudinary `StorageService` (the interface exists from Phase 10 specifically so this is a drop-in swap). For a demo, this is acceptable — just don't rely on old uploads surviving a redeploy.

**Alternative — Railway:** same idea. New Project → Deploy from GitHub repo → set root directory to `backend`, Railway detects the Dockerfile. Set the same env vars in the Railway dashboard. Railway's free trial credits vary; check current terms.

---

## 3. Frontend — Vercel (or Netlify)

Vite bakes `VITE_API_URL` into the bundle **at build time**, so set it **before** the first deploy.

**Vercel:**
1. https://vercel.com → **Add New → Project** → import your repo.
2. Set **Root Directory** to `frontend`.
3. Framework preset: Vite (auto-detected). `frontend/vercel.json` already handles the SPA rewrite so refreshing on `/student/dashboard` doesn't 404.
4. **Environment Variables** → add `VITE_API_URL` = your Render backend URL (e.g. `https://ecoquest-backend.onrender.com`, no trailing slash).
5. Deploy.

**Netlify (alternative):** same steps; `frontend/netlify.toml` already contains the build command, publish dir, and SPA redirect. Set `VITE_API_URL` under Site settings → Environment variables, then trigger a deploy.

---

## 4. Wire them together

1. Go back to Render → your backend service → **Environment** → set `CORS_ALLOWED_ORIGINS` to your exact Vercel URL (e.g. `https://ecoquest-india.vercel.app`). Multiple origins can be comma-separated. Save → Render redeploys.
2. Open the Vercel URL, register an account, and walk the demo flow.

**If you see CORS errors in the browser console:** the value in `CORS_ALLOWED_ORIGINS` doesn't exactly match the origin the browser is sending (check for `http` vs `https`, a trailing slash, or `www.`).

---

## 5. Seeding the first admin

Registration through the UI only offers Student and Teacher roles by design. Create the first admin directly against the API once:

```bash
curl -X POST https://<your-backend>/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"name":"Admin","email":"admin@ecoquest.com","password":"<choose-a-strong-one>","role":"ADMIN"}'
```

The backend allows this **only while zero admins exist** (`AuthService.register`). After the first admin exists, any further public registration attempt with `"role":"ADMIN"` is rejected with `403`. **Do this step immediately after deploying** — until the first admin exists, anyone who finds the endpoint could claim it. Additional admins would need to be created by a seed script or a future admin-only "create admin" endpoint (not built yet — listed in Future improvements).

## Environment variable reference

| Variable | Where | Purpose |
|---|---|---|
| `MONGODB_URI` | backend | Atlas connection string |
| `JWT_SECRET` | backend | ≥32 chars; signs auth tokens |
| `CORS_ALLOWED_ORIGINS` | backend | Comma-separated allowed frontend origins |
| `AI_PROVIDER` | backend | `mock` (default) or `gemini` |
| `GEMINI_API_KEY` | backend | Only needed if `AI_PROVIDER=gemini` |
| `FILE_STORAGE_PATH` | backend | Local upload dir (ephemeral on Render free tier) |
| `MAX_UPLOAD_SIZE` | backend | e.g. `5MB` |
| `VITE_API_URL` | frontend (build-time) | Backend base URL |
